## 0. 首页：推荐组合、成立条件、收益与代价（CANDIDATE）

### 0.1 推荐（组合建议，不是唯一赢家；仍由用户裁决）

1. **主运行骨架仍建议 A2＝PydanticAI Core（`pydantic-ai-slim[provider]`）＋按需 Harness。** 沿用 framework-04/05/06 的候选建议，本轮按「职责承载＋可修改性」两条新维度复核后**未被推翻**。
2. **调度与检测按层次选承载方**：Core/Harness不是完整持久调度服务，可用官方配套／durable engine、成熟外部设施与必要检测适配。框架配套仍可在组合内承担，ADR-002未指定必须项目自建。单独加入Pi未证明带来持久调度增量；不是“三候选及配套恒无调度”。
3. **A1保留条件性候选**：须证明相对A2及其配套的目标版本净收益，来源可以是执行面、模型／资源接入、交互或实际组装维护便利，不限于“隔离执行面是一等需求”。计入双运行时与跨边界配置／恢复成本；尚未选A2或否定A1。
4. **LangGraph** 仅在图流程／状态机或需要现成 cron／队列／多 worker／webhook（部署层，许可受限）时回查；本轮不重比。
5. **可修改性结论（条件化）**：把「日常内容与参数」与「结构／流程维护」分开；**不承诺「连上界面即可改一切」**，也不以「文件多／扩展多」作为维护优势。

## 2. 职责同表：实际由谁承担（A2 vs A1）

> 每格标五层。完整逐格证据（含源码位置与旧原型实跑记录）在两份依据报告与 framework-06 §2；本表是主窗口收敛版。

| 职责 | 必须说明的点 | A2（PydanticAI Core＋按需 Harness） | A1（＋Pi 执行器） | A1 相对 A2 |
|---|---|---|---|---|
| **① 主会话与本人任务／子代理** | 模型工具循环、独立工作、并发／等待／取消、结果回流、主对话继续（**等待 delegate ≠ 进程不能并发**） | ① `Agent` typed tool loop＋`message_history`；② Harness `SubAgents.delegate_task`：子代理**独立 run/独立 history**、per-delegate `max_calls`／`timeout_seconds`／`usage_limits`／`contain_errors`；① asyncio 并发（`max_concurrency`／`ConcurrencyLimit`）＋取消；旧原型已验 parent→child→parent 与取消传播。仍缺④：异步后台 worker、父子授权 scope | ① 主会话仍在 PydanticAI；④ 加 Python→Pi 桥把 Pi 当工具调起；①（Pi 侧）`AgentSession` 自带循环／`steer`／`follow_up`／`abort`。仍缺⑤：双层循环的模型出口设计 | **不加**运行单元，**多一层**执行器循环 |
| **② 定时与外部条件** | 登记／撤销／去重／补检与来源检测须有具体承载 | Core/Harness不足以全包；官方配套／DBOS等engine或成熟外部设施可承担部分登记、队列、去重与补检，剩余适配按目标组合核对 | 宿主配套同A2；Pi进程内timer不替代持久调度 | 单独加入Pi未证明持久调度增益；不预定项目自建全部 |
| **③ 受控工具与 authority** | 谁检查资格／签发 receipt、谁执行工具、谁提交认领与成果；A1 跨栈由谁归口 | ① 能力生命周期 hook（`after_tool_execute` **旧原型已实跑**）＋`requires_approval`／deferred；④ receipt 自写；签发归口与执行前检查仍需接线，after_tool_execute旧证据不证明执行前授权。限定：`FileSystem.root_dir` 只限文件工具、**非 OS 沙箱** | ① 宿主同一 hook；①（Pi 侧）extension `tool_call` 可 block＋`appendEntry`。默认不逐次询问用户不等于无法逐工具检查；除调起Pi外可在受控tool_call路径落实资格检查，具体接线未验；扩展以完整系统权限运行、**非沙箱** | **多一个**潜在 authority 位点，须**唯一归口**（否则违反 00c §9.1） |
| **④ 恢复与作品** | session 重开／run 恢复／从任务成果继续各覆盖什么；效果未知或回执丢失怎样核对，**不把重放当成功** | ① `message_history`（序列化往返**未验**）；② `StepPersistence` settled 快照＋tool-effect ledger（`started/completed/failed`／`unknown_after_crash`）；② 同 run 工具中途续跑需接**一个** engine（旧原型未接）；③ 外层 manifest/artifact 从作品续做（**已验**） | 宿主侧同上，但 ledger **只覆盖「调起 Pi」这一层**；①（Pi 侧）session entry tree 重建（可能被 compaction 摘要）→ **两套会话无共享契约**；Pi **无 durable** | **多一套**会话存储＋**跨栈对账缺口** |
| **⑤ 界面与运行管理** | 主动结果、无文本结束、断线恢复、配置读取各由谁承担（只到职责，不写接口/页面） | ①/② `UIAdapter`→SSE、`UIEventStream`；④ 主动递回／无文本结束／断线恢复在**自有鉴权路由**（适配器端点不是鉴权边界） | 宿主同 A2；①（Pi 侧）事件流；④ 需把 Pi JSONL 事件映射回宿主 UI 事件 | **多一层**事件翻译；无文本结束判定更薄 |
| **⑥ 维护与部署** | 必须／按需依赖、常驻进程、存储、升级与排障、配置源及桥接（无数字） | ① `pydantic-ai-slim[provider]` 单包；② 按需 harness；② 按持久等待／调度／同run恢复需求考虑engine；单 Python worker；调度按②／③／剩余④适配核对 | ① 宿主栈＋① Pi 包＋Node 运行时的**两栈**；Python 宿主进程＋Pi Node 长驻子进程；**两语言／两会话存储／多个配置消费者，不必两份真源** | **两栈**版本／会话／配置都要跟 |

**分层核查（沿用 framework-06 §2 结论）**：核心库循环 ≠ 完整持久调度／独立业务 worker／OS 沙箱；② 层（engine／部署层／官方可选 workspace＋sandbox）与 ③ 层都可以承担部分责任，但**目标组合尚未核验**，不据此说三者「完全没有配套」。

## 3. A1 的净增量收益与代价（卡 §3 要求单列）

**正增量**：① 执行面套件打包（四种外部隔离部署指导／MCP／Code Mode／skills／prompt 模板／自定义 provider／会话期长资源）——**须扣除 A2 官方可选项**（Shell／Modal Sandbox／Code Mode／MCP／Browser Use／Playwright）；② Pi 路径已有固定版本实跑（RPC 工具循环、会话存储、`context` 注入、大结果 spill）与 Linux 同会话跨进程恢复／退出实测；③ 执行侧天然是独立 OS 进程，长执行不占宿主事件循环。

**负增量**：① 双层 agent 循环（谁持模型出口、调用是否翻倍未设计）；② 双会话/双账本无共享契约（`StepPersistence`＋`conversation_id` vs Pi session tree）；③ authority 可能双位点，须归口；④ Python↔Node 桥（严格 `\n` 分帧、按 `id` 关联、等 `agent_settled`、事件映射）；⑤ 跨运行时副作用对账（Pi 内部工具崩溃不在宿主 ledger 内）；⑥ 两栈版本/会话格式/配置对齐＋Pi Windows 退出语义仍未解释。

**判断口径（沿用 framework-06 复核 §4）**：不要求 A1 收益「只来自独有功能」；**也不因「Pi 在 Linux 退出干净」就选 A1**；「要隔离执行」本身不足以选 A1，须证明目标版本实际净收益，不能仅以隔离需求或功能集合更大作前提。

### 4.1 「保存值 ≠ 生效值」的结论（回答用户原问的关键）

1. **能保存、运行会采用、什么时候采用是三件事。** 前端与后端接通只解决「界面能编辑后端允许改的内容」。
2. **没有任何一个框架保证「改磁盘或界面值后，所有活跃 session／子进程／扩展自动同步」。** 已核实的强证据：Pi `settings.md` 明写 `/reload` **只启用新加进 `defaultTools` 的工具，不移除被删的、也不重新启用你手动关掉的工具**；Pi 有 `session.systemPrompt`（只读，含尚未发给模型的改动）与 `getActiveToolNames()` 可作「当前有效值」的读取来源；PydanticAI是否改变须区分instructions、standing system_prompt和动态参数；已有run不等于全部值冻结。
3. **因此候选答案是**：由**项目侧**维护并展示一份「当前有效配置/版本」视图（每会话/每 run 的生效点与所用版本），而不是靠「保存成功」提示。具体形态仍 OPEN，本报告不给字段/接口。
4. **旧任务采用旧配置还是新配置，不能一律热更新**：按类分别给候选策略（①②③④表内），且**撤销权限不得因配置回退而隐含恢复**——须把撤销实现为独立权限状态，而非一个可回退的配置开关。

## 5. 两个变更纸面场景（虚构资料，非运行验收）

### 5.1 场景一 · 长任务中改设定和模型

设定：一个虚构研究任务在跑，同时有一个**只读子代理**在运行；用户（a）改表达偏好、（b）切模型。

| 观察点 | A2 | A1 |
|---|---|---|
| 主对话**下一请求** | 当前instructions可重新求值，是否采用新偏好由数据源／版本策略决定；历史system_prompt与旧普通内容分别处理，不能把“不新建system_prompt”套用于instructions | 同A2；仅Pi也消费的项需向其投送新视图，不要求用户两边手改 |
| 只读子代理**当前工作** | 子代理是独立 run／独立 history，其内容与模型在**创建时**确定→**继续按旧设定/旧模型跑完** | 同 A2；若子代理是另起的 Pi 进程，其模型/资源由该进程启动参数决定→**进程内不随宿主改动** |
| 任务**重启后**读取 | 从序列化 `message_history`＋任务/作品记录恢复；历史若带旧指令，重启**可能重新采用旧文本**，除非显式重建注入并带 content 版本 | 两侧各自恢复（编排侧 `message_history`＋`StepPersistence`；Pi 侧 session entry tree，可能被 compaction 摘要）；**两套会话无共享契约** |
| 旧内容与新设定**怎样区别** | 靠**项目侧 content 版本／watermark**（该会话/该 run 用哪版），**不能靠比对提示词文本差异** | 同 A2，另需标记 Pi 侧资源版本并对齐 |

### 5.2 场景二 · 撤销工具资格并调整定时查看

设定：任务在等明天查看某个虚构论坛；用户（a）撤销写文件资格、（b）改查看时间。

| 环节 | A2 | A1 | 必须单独核对的点 |
|---|---|---|---|
| 既有**登记** | 登记＝项目数据；改时间＝改登记值。候选：旧登记保留旧值（快照）或改后重读（重写）——未定 | 同 A2（Pi 无原生调度） | 已完成效果保留，排队／已触发项处理未定；去重/补检仍 OPEN（Q-MA-04） |
| **下一次受控工具调用** | Host 在调用前检查**当前 capability**：写文件资格已撤销→**拒绝**（不是靠改提示词） | 同 A2；Pi 侧 extension `tool_call` 可 block，但非沙箱，绕过该路径的动作不受约束 | 撤销的**时点**：已通过检查的在途调用是否中止属契约，未定 |
| **已完成效果** | 已写入的文件/外部效果**保留**，撤销不反向执行；历史 receipt 保留但不再授予权限 | 同 A2 | 不靠重放补编成功，也不指望撤销自动回滚 |
| **配置回退** | **单独核对**：若「写文件资格」被实现成配置开关，回退可能**隐含重新授权**→须实现为独立权限状态 | 同 A2（且两侧各有一套配置，回退须指明退哪一侧） | 讨论记录 §4 已列同名 OPEN |

## 6. 对 memory-affect 七组裁决与三档的影响

### 6.1 七组裁决

- **七组裁决均不被推翻**；Host 仍是「可信检查＋receipt 签发」的**职责**而非旧类名。
- **authority归口对A2/A1都成立**：按独立domain明确主体决定、签发与执行检查责任，多位点检查可复用同一决定；A1额外核对跨栈传播与覆盖范围。A2同栈并非天然已满足，不把所有domain合成一个签发者。
- **框架覆盖与适配按层核对**：调度可由官方配套／engine／成熟设施承担，来源检测另核；A2也可用进程或外部worker，Pi子进程不构成独有隔离优势。不恢复ADR-002已退出的模拟机制。
- **Affect/Need 读时推导与框架选择无关**：两者都不需要为刷新数值安排持续模型唤醒。

### 6.2 对 Light / Balanced / Full 的影响

| 维度 | A2 | A1 |
|---|---|---|
| 本人任务/子代理 | 同进程 `SubAgents`＋按需后台 worker；Light 的串行排队最自然 | 宿主并发＋Pi 子进程名额**两层**资源协调；Light「一次一个 Pi 进程」较自然 |
| 时刻/条件监听 | 按配套／engine／外部设施与检测接入划分；Balanced安排仍候选 | 同 A2，另加触发后「再调 Pi」一跳 |
| 恢复与历史重评 | 单会话＋单 ledger，按稳定检查点补缺口 | 双会话＋跨栈对账，补缺口须覆盖 Pi 侧 |
| 增减接线成本 | 单栈，增项集中在业务平台件 | **两栈**：桥／双存储／跨栈归口／对账是**固定增量，不随档位减少** |
| Full 的多消费者/多长期任务 | 多任务→多 worker/engine（按需） | 多长期任务→多 Pi session 归口＋跨栈对账，观测/排障面最大 |

三档共享本体与 authority 不变；**Balanced 仍是比较建议，不因本报告被确认**；本报告与两份依据都不选档。

## 7. 仍未验与一项影响选择的窄验证建议

### 7.1 仍未验（合并两份依据，去重）

1. A1 双层 agent 循环语义（模型出口、调用倍率、跨等待期消息/取消）——未验。
2. A1 跨运行时副作用对账与幂等 key 归口；桥的无损映射、两套会话格式与两套配置对齐——未验。
3. A1 authority 跨栈归口——未验（决定选 A1 前的前置）。
4. A2 `message_history` 序列化往返恢复；同 run 工具中途续跑（未接 engine）——未验。
5. 两者共同的：**无文本结束（沉默）**、真实模型/Serein、OS/容器隔离与凭据边界、并发副作用 exactly-once——未验。
6. Pi Windows `0xC0000409` 根因**未解释**（Linux 108/108 exit 0 只作局部条件证据，不外推）。
7. 官方依据对应性：Harness **0.36.0** 仅见锁文件；滚动 0.x 文档不保证逐条对应；现行四层顺序已确认，固定版本支持与接线未验；Pi v1.0.4 RPC 手动词表是否含 `compact` 未确证。
8. 配置生效边界：Pi `/reload` 的「删工具不失效」等行为**只见文档、未实跑**；「改磁盘→活跃 session 自动同步」**无任何官方保证**；A1 两侧配置优先级**无官方规定**。
9. 认知/契约层：Q-MA-02 至 07、Q-CTX-01 全部保留。

### 7.2 一项窄验证建议（CANDIDATE，只建议、不执行；需用户另开范围）

**目标**：验证「**配置编辑的生效边界**」——即「保存值 ≠ 当前生效值」是否可被使用者观测，以及 Pi 文档中反直觉的 `/reload` 行为是否成立。理由：这是可以帮助配置加载设计的一项未知，不是唯一选型阻断项；它直接回答用户原问，且比 A1 跨运行时对账更便宜、更早可做（后者只在用户倾向 A1 时才需要）。

**做法**（离线、脚本化模型桩、无网络、无产品库、不接 Serein；本轮不运行）：
- (a) 若采用Pi路径，先核对固定版本SDK／RPC支持的重载与查询入口，再检查删除defaultTools项后的当前工具集合；getActiveToolNames是SDK方法，不当作RPC命令。SDK普通reload与RPC/prompt slash是否对应先查，未确认前不写可直接执行。
- (b) 同会话改一处 instructions／资源，观察**下一请求**是否采用新值、`session.systemPrompt` 是否变化。
- (c) PydanticAI分两组：动态instructions＋既有history（读活数据或固定版本）；standing system_prompt＋既有／缺失system prompt历史（含ReinjectSystemPrompt）。只记录新请求实际发送的内容，不以旧历史里存有文本判定当前指令仍有效。

**通过条件（全部满足）**：(a) 能区分「文件值/保存值」与「当前有效值」并给出两者的可读来源；(b) 能复现或明确推翻「删除的工具在 reload 后仍可用」；(c) 全程无非 loopback 连接、未接产品库、未接正式凭据。

**若用户倾向 A1，另需（本轮不列入建议、不执行）**：跨运行时契约的最小离线验证（宿主调 Pi 写副作用→写盘后记账前杀进程→重启仅凭外层记录判定「已完成/未知」且不重复写）。它只在 A1 已被判定值得考虑后才有意义。
