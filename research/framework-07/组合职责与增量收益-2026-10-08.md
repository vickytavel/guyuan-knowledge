### 0.1 六职责同表（A2 vs A1，最小必要组件／承载层／仍缺接线）

| 职责 | A2（PydanticAI Core ＋ 按需 Harness，比较基线） | A1（PydanticAI ＋ Pi 执行器） | A1 相对 A2 的判读 |
|---|---|---|---|
| ① 主会话与本人任务／子代理 | ① `Agent` 工具循环＋`SubAgents`（同进程、父 run 内一次工具调用）；① `message_history`；① asyncio 并发（`ConcurrencyLimit`）+ 取消。旧原型已验 parent→child→parent。仍缺④：异步后台 worker、父子授权 scope | ① 主会话仍在 PydanticAI；④ 另加 Python→Pi 桥，把 Pi 当工具调起，①（Pi 侧）`AgentSession` 自带循环 → **双层 agent 循环**。仍缺⑤：谁持模型出口的显式设计 | **不加**运转单元，**多一层**执行器循环 |
| ② 定时与外部条件 | ⑤ Core/Harness 无调度（Harness issue #111 未合并）；②／③配套或成熟调度设施＋必要来源检测与剩余业务适配 | ⑤ 宿主侧同 A2；⑤ Pi 侧也无调度（extensions 禁 factory 起 timer）；④ 同上 | **无增量**，承载层未定，单独加入Pi未证明增益 |

| ⑤ 界面与运行管理 | ①/② `UIAdapter`→SSE、`UIEventStream`；④ 主动/无文本递回、断线恢复在自有鉴权路由 | 宿主同 A2；①（Pi 侧）事件流；④ 需把 Pi JSONL 事件映射回宿主 UI 事件 | **多一层**事件翻译；无文本结束判定更薄 |
| ⑥ 维护与部署 | ① `pydantic-ai-slim[provider]`；② 按需 harness；② 按持久等待／调度／同run恢复需求考虑engine；单 Python worker | ① 宿主栈 ＋ ① Pi 包 ＋ Node（**两栈**）；Python 宿主进程＋Pi Node 子进程；**两语言两会话存储** | **两栈**版本/会话/配置都要跟 |

### 0.2 A1 净增量收益（相对 A2 及其配套；卡 §3 要求单列）

**正增量（收益）**

1. **执行面套件是打包的（②/①，Pi 侧）**：Pi v1.0.4 文档列四种外部隔离部署指导（Plain Docker、Docker Sandboxes、NVIDIA OpenShell、Gondolin 微 VM）、`mcp.md`、`codemode.md`、skills/prompt-templates、`registerProvider`/`registerVirtualModel`、`session_start` 起的会话期长资源。这些是 A2 需另接/另选的东西。
   **但须按目标版本比较，不能全计作自建**：PydanticAI 现行文档（2026-10-08）同样列出可选 `Shell`、`Modal Sandbox`、`MCP`、`Code Mode`、`Browser Use`、`Playwright` 等官方可选能力；A1 的收益只在**目标版本**确证「Pi 打包集 > A2 可选集且更合适」时成立。
2. **Pi 路径已有固定版本实跑记录**：RPC 工具循环、会话存储、`context` 注入、`tool_result` spill（framework-04/05），且 **Linux 侧同会话跨进程恢复与退出已实测**（84/84，另有 P1/P2 补测；见 [补充-Linux退出与恢复验证](../framework-06/补充-Linux退出与恢复验证-2026-10-07.md)）。
3. **执行侧天然是独立 OS 进程**：长执行不占宿主事件循环（④，宿主消费 JSONL 事件）。

**负增量（成本，必须与收益一并评估）**

1. **双层 agent 循环**：Pi 本身是完整 agent 运行库；A1 = 「宿主编排 run」内嵌「被委派 Pi run」，谁持模型出口、模型调用是否翻倍须设计（⑤未验）。
2. **两套会话/checkpoint 存储、无共享契约**：宿主 `StepPersistence`＋`conversation_id` 与 Pi session tree 各自持有，不可跨执行器通用迁移（framework-04 §4）。
3. **authority 可能双重出现**：宿主 hook 与 Pi 扩展都要做检查/签发 → 须按domain明确决定／签发者与执行检查，多个检查点可复用同一权威决定，否则违反 00c §9.1「不能两边各自宣称完成或授权」。
4. **Python↔Node 桥**：严格 `\n` 分帧、按 `id` 关联、等 `agent_settled`、事件→工具结果映射（④）。
5. **跨运行时副作用对账**：Pi 子进程内部工具中途崩溃**不在**宿主 tool-effect ledger 覆盖内（④/⑤未验）。
6. **两栈维护＋Pi Windows 退出语义未解释**：`0xC0000409` 仍是未解释的 Windows 现象，**不以「Linux 退出正常」自动支持 Pi**（卡 §3 明令）。

**一句话**：A1 的收益集中在**执行面/隔离套件与模型服务接入的打包**（且须扣除 A2 的官方可选项），代价集中在**双运行时／双会话／跨栈归口与对账**。核心循环未全包持久调度，官方配套／engine／成熟设施可承担，不能把②层写成恒为项目自建，authority/receipt（③）与恢复归口（④）在两者中都需项目适配。

## 2. 六职责逐格同表（A2 vs A1）

### 2.1 职责①：主会话与本人任务／子代理

| 子项 | A2 | A1 |
|---|---|---|
| 主会话模型/工具循环 | **①** `Agent`（`run`/`run_sync`/`run_stream_events`/`iter`）typed tool loop；① `deps_type`+`RunContext`；① `message_history`。旧原型已验：framework-04 `prototype.py`、framework-05 `pai_run.py`/`pai_history.py` 实跑工具循环与状态注入。 | **①** 主会话同样在 PydanticAI `Agent.run`；**④** 另加 Python→Pi 桥把 Pi 当一次工具调用调起；**①（Pi 侧）** `AgentSession` 自带完整工具循环／`steer`/`follow_up`/`abort`。仍缺：双层循环的模型出口与调用倍率设计（⑤未验） |
| 独立工作（本人 vs 代做） | **②** Harness `SubAgents`/`SubAgent`：`delegate_task(agent_name, task)`，子代理**独立 run、独立 message history**，per-delegate `max_calls`/`timeout_seconds`/`usage_limits`/`contain_errors`。旧原型已验：framework-04 `run_validation.py` D1 parent→child→parent。**③**（旧项目资产）外层 ArtifactStore 收产物。仍缺④：父子 actor/授权 scope、异步后台 worker | **②** 宿主同一 `delegate_task` 可复用，但其「下手」是 Pi 子进程（④）；或 **④** 宿主另起独立 Pi RPC 进程/session。仍缺⑤：Pi **无子代理原语**（v1.0.4 与 main 全 40 份文档 grep `sub-agent\|subagent` 零命中）；Pi 侧无父/子 history 隔离与 per-delegate 预算 |
| 并发／等待／取消 | **①** `agent.run` 为 async；`max_concurrency`/`ConcurrencyLimit(max_running, max_queued)`＋`asyncio.gather`（**现行文档声称**，2026-10-08）；① `CancellationToken`/`ctx.cancel()`/`RunCancelled`。旧原型已验取消传播到 async tool。**关键限定（卡 §3）**：父 run 等本次工具结果 **≠** 整个进程/主对话被占住。仍缺④：CPU/同步阻塞与持久资源边界 | 同 A2 宿主侧并发；**④** 执行侧 Pi 子进程**天然是独立 OS 进程**，可承载长执行（宿主消费其 JSONL 事件）。仍缺⑤：跨栈取消（宿主取消是否传播到 Pi 子进程、Pi `abort` 语义）、多 Pi 子进程关闭时序未验 |
| 结果回流与主对话继续 | **①** 子代理 output 回父 run（`str(result.output)`）；**③/④** 回流、跨等待期排队与主动回流业务层自写 | **④** 宿主桥把 Pi 事件/工具结果映射回 PydanticAI 工具返回；主对话继续在宿主主会话。仍缺④/⑤：映射无损性、Pi 子会话与宿主主会话无共享契约 |

### 2.2 职责②：定时与外部条件

| 子项 | A2 | A1 |
|---|---|---|
| 注册／撤销／去重／停机补检 | **⑤** Core/Harness **无调度**（Harness issue #111 未合并；core 亦有对应 open issue）；②／③配套／engine或成熟设施的登记／取消／去重／补检能力先核对，剩余才④适配 | **⑤** 宿主侧同 A2；**⑤（Pi 侧）** Pi 也无调度（`extensions.md`：factory 禁起 processes/sockets/watchers/timers；`session_start` 起的 timer 随进程死亡，**不构成重启可补检调度**）；**④** 同上。**A1 不比 A2 多调度能力** |
| 检测数据接入 | **④** 项目工具抓取/条件判断；框架 timer 到点**不知道内容变化** | **④** 同（Pi 也不提供数据检测） |
| 到点触发一轮 | **①** 触发一次新 `Agent.run` | **④** 触发宿主 run，宿主再调起 Pi（**多一跳/多一进程**） |
| 可选框架配套／成熟设施 | **②** DBOS Cron/Queues 属 engine 层（**仅接 DBOS 才有**）；**②** LangGraph 部署层 cron（本报告不重比） | 同 A2（Pi 无对应） |

### 2.3 职责③：受控工具与 authority（A1 跨栈归口在此）

| 子项 | A2 | A1 |
|---|---|---|
| 谁检查资格／签发 receipt | **①** 能力生命周期 hook（`before/after/wrap_run`、`after_tool_execute` **旧原型已实跑**）＋ `requires_approval`/`DeferredToolRequests`/`CallDeferred`/`HandleDeferredToolCalls`（现行文档声称）；**④** receipt 自写（框架**无 receipt 类型**） | **①** 宿主同一 hook 位点；**①（Pi 侧）** extension `tool_call` 可 `block`、`registerTool`/`appendEntry`。仍缺⑤：**跨栈归口未定**——宿主 hook 与 Pi extension 可能**同时存在** |
| 谁执行工具 | **①** 进程内工具（Harness `FileSystem(root_dir=...)` 等）。**限定**：`root_dir` **只限文件工具、不是 OS 沙箱**，`Shell` 不受其约束（⑤） | **①（Pi 侧）** Pi 执行工具；**关键约束**：默认不逐次询问用户不等于只能在调起Pi时检查；可通过受控tool_call等路径落实逐工具检查，实际接线与不可绕过范围未验 |
| 谁提交认领与成果 | **④** 业务层提交；真值来自**执行端 receipt**，框架记录不证明业务完成 | **④** 同；跨栈副作用须另设幂等键（⑤未验） |
| **A1 跨栈归口（核心风险）** | 同主技术栈便于归口，但签发／执行检查接线仍未验，不自动满足 | 须明确**唯一归口**：按domain明确签发归口，宿主hook与Pi extension可各作执行检查；否则违反 00c §9.1「**不能两边各自宣称完成或授权**」。当前 **⑤未验** |

### 2.4 职责④：恢复与作品

| 子项 | A2 | A1 |
|---|---|---|
| session 重开 | **①** `message_history`（`ModelMessagesTypeAdapter` round-trip；**序列化恢复旧原型未验**） | 宿主侧同上；**①（Pi 侧）** `SessionManager`/`--session` 会话重建（entry tree，可能被 compaction 摘要）→ **两套会话存储、无共享契约（④）** |

| 从任务／成果继续 | **③**（旧项目资产）外层 manifest/artifact（framework-04 L1/L2、framework-05 C5B 已验「从作品续做」） | **③** 同（两侧都支持，可迁移，凭外层契约） |
| 工具效果未知／回执丢失核对 | **②** ledger ＋ **③** artifact 版本/哈希；**不把重放当成功**（真值来自执行端 receipt） | 宿主 ledger 覆盖不到 Pi 内部；须**跨运行时幂等 key/对账**（⑤未验）；两套记录谁为准未定 |

### 2.5 职责⑤：界面与运行管理

## 4. 三纸面场景：只补会改变组合判断的差异

沿用 framework-06 §4 分析，**只列 A1 与 A2 会分叉、且会影响组合判断的点**（虚构资料，纸面推演，非运行验收）。

| 场景 | A2 关键点（已复用） | **A1 的分叉点（本报告新增）** | 是否改变组合判断 |
|---|---|---|---|
| 1 研究期间继续交谈 | 父 run 等 `delegate_task` 结果**不阻塞其它异步 run**；主对话可另起 `Agent.run(message_history=…)` 继续（**现行文档**；旧原型已验委派同进程） | 主会话在宿主，被委派 run 再调 Pi 子进程 → **双层循环**；等待期用户消息投给**宿主主会话**，与 Pi 子进程内会话**无共享**。若要「真后台」须宿主并发＋多 Pi 进程 | **是**：A1 多一层执行器循环与跨栈消息/结果映射（覆盖面而非能力面） |
| 2 真实时刻／回复变化 | 定时**不在框架内**（⑤）；到点触发新 run；检测/去重/补检/沉默全在项目侧（④）；无文本结束未单独验证 | 宿主侧同；到点触发宿主 run 后**再调 Pi（多一跳/多一进程）**；「无文本结束」须从 Pi 事件判定（Pi 原型 D2 仍产文本，⑤） | **否（对定时能力）**：A1 不比 A2 多任何调度；**是（对递回链）**：沉默递回多一层事件翻译 |
| 3 停机后继续创作 | `message_history`（序列化未验）＋ settled 快照＋ ledger（`unknown_after_crash`）＋从作品续做（已验）；同 run 中途需 engine（未接） | 宿主侧同上，**但 ledger 覆盖不到 Pi 内部副作用**；须跨运行时幂等键/对账；**多一套 Pi 会话**须归口；Pi 同会话跨进程恢复 Linux 已验、Windows 旧原型 `0xC0000409` | **是**：A1 恢复面多一个执行器会话与跨栈对账缺口 |

**共同缺口（两列一致，不因选谁消解）**：外部变化检测、登记/去重/停机补检、无文本结束、真实模型/Serein、OS/容器隔离与凭据边界、并发副作用的 exactly-once 全部未验。

## 6. 仍未验与一项影响选择的窄验证建议

**仍未验清单（本报告范围内）**

1. A1 **双层 agent 循环**语义：谁持模型出口、模型调用是否翻倍、跨等待期消息/取消语义——**未验**。
2. A1 **跨运行时副作用对账**：Pi 内部 tool 崩溃是否被宿主 ledger 覆盖、幂等 key 归口——**未验**。
3. A1 **authority 跨栈归口**：宿主 hook 与 Pi extension 的主从/唯一性——**未验**。
4. A1 **桥无损性**：Python↔Node 事件/结果映射、两套会话格式归口、两套配置对齐——**未验**。
5. A2 **`message_history` 序列化往返恢复**、**同 run 工具中途续跑（未接 engine）**——**未验**。
6. 两者共同的**无文本结束**、**真实模型/Serein**、**OS/容器隔离与凭据边界**、**并发副作用 exactly-once**——**未验**。
7. **Pi Windows 退出语义** `0xC0000409` 根因——**未解释**；Linux 侧 108/108 exit 0 只作「该场景/该 Node 版本未在 Linux 复现」，**不外推**。
8. 官方依据对应性：**Harness 0.36.0 仅见于旧原型锁文件**，滚动 0.x 文档能力**不保证**与 0.36.0 逐一对应；Pi v1.0.4 RPC 手动词表是否含 `compact` **未确证**。

**一项影响选择的窄验证建议（CANDIDATE，仅建议，不执行）**

- **目标**：检验 A1 相对 A2 唯一的新增风险面——**跨运行时业务契约能否无损跨越边界且重启不重复外部副作用**。
- **做法（离线、脚本化模型桩、无网络、无产品库、不接 Serein；本轮不运行）**：宿主调起一个 Pi RPC 子进程执行**一轮带副作用**的工具（写一个带内容哈希的作品）；宿主侧记该 `tool_call_id`；在 **Pi 写盘后、宿主记账前**杀进程；重启后**仅凭外层记录**判定「已完成/未知」，**只读确认/续做**（不重复写）。附测：Pi 以 `--session-id` 重开能否重建上轮 entry 且退出码 0。
- **通过条件（全部满足）**：(a) 宿主能区分该 `tool_call_id` 的「已完成/未知」；(b) 业务侧据此判定后**不重复写入**（文件哈希不出现第二版）；(c) Pi 侧跨进程重开能重建上轮 entry 且两次退出均为 0；(d) 全程无非 loopback 连接、未接产品库。
- **理由**：若通过，A1 双运行时路线在该需求下成立；若不通过（尤其 (b)/(c)），则该需求下 **A2（单运行时）优先**，Pi 仅保留为工具面而非「手脚」运行时。**只建议，不执行**（卡 §3/§7）。
