## 1. 口径、证据纪律与一句话结论

- **不能以「可配置／扩展自由／Python 容易改」代替证据**：本报告对每类改动给出「改了什么 → 谁读 → 何时生效 → 对旧对象的影响 → 是否要代码/迁移 → 谁校验留版本」，并明确**保存值≠当前生效值**。
- 用户原问「只要前端和后端配置连上了基本都能改吗」的候选答复：**能保存、运行会采用、在什么时候采用是三件事**（讨论记录 §2）。前后端接通只解决「界面能编辑后端允许改的内容」，不解决生效点、旧任务采用旧值还是新值、以及权限/认领是否被绕过。
- 层次图例（沿用候选报告）：①框架核心原生 ②官方可选能力或部署层 ③已有项目资产 ④必要新增适配 ⑤尚缺或未验。
- 版本锚点（见 §5 与 §7）：PydanticAI Core **2.51.0** ＋ Harness **0.36.0**（旧原型锁文件）；Pi `@earendil-works/pi-coding-agent` **v1.0.4**（tag `v1.0.4`＝commit `7c10bd43`，2026-10-05；npm `latest` 亦 1.0.4）。
- **一句话结论（CANDIDATE）**：六类改动里，①内容/设定、②部分模型与工具参数、④已有工具的启用与权限配置，**在框架层存在"可配置"的接入点**；③调度与预算、⑤认知参数与长期设定、⑥流程与结构，**要么落在项目侧、要么需要主体认领或代码/重启/迁移**。A1 相对 A2 **不减少**任何一类改动的类别，反而在涉及两侧消费的项多一道映射／加载边界，不必多一份配置真源，因此「哪个更好改」没有跨类统一赢家，取决于该改动是否恰好落在某个框架的既有接入点上。

## 2. 六类实际改动·主表

> 生效点术语：**下一请求**＝同会话下一次模型请求前重新求值；**下一 run**＝新一次 agent run 读取新值；**边界重载**＝框架/适配在受控边界重新加载配置；**重启**＝进程重建；**迁移**＝数据/结构改写。

| # | 类型 | 使用者改什么（例） | A2 实际生效点 | A1 实际生效点 | 是否需代码/迁移 | 旧任务候选策略（不强制热更新） |
|---|---|---|---|---|---|---|
| ① | 内容与设定 | 世界书条目、表达偏好、提示词/技能说明 | 动态 instruction（`@agent.instructions`）**每请求重求值**→下一请求生效；静态 `instructions=` 文本在 `Agent` 构造时确定→需重建/新 run。`message_history` 非空时**不重新生成系统提示** | Python 编排侧同 A2；另加 Pi 侧 `SYSTEM.md`/`APPEND_SYSTEM.md`、`AGENTS.md` 上下文、skills、prompt 模板（`ResourceLoader` 加载，项目 `.pi` 于 trust 后加载）→Pi 侧需 `/reload` 或重开会话 | 增改内容通常仅数据/文件；若把「内容」编进 `Agent(...)` 字面量或扩展代码则需改代码 | **默认旧会话保留旧历史文本**（历史不可静默改写）；新请求读新值；要改在途会话需显式重建或显式注入 |
| ② | 模型与工具参数 | 换模型/provider、输出长度、工具超时 | 换模型可**每 run 指定**；`model_settings` 分层（模型默认→agent→capability→run），run 级最高，可为**每请求求值**的可调用对象；agent 级/模型级需构造时确定 | 编排侧同 A2；另加 Pi 侧 `--provider/--model`、`models.json`、`defaultModel`/`defaultThinkingLevel`、`compaction.modelOverrides`、`retry.provider.timeoutMs`。**两侧各有一个模型出口** | 一般只改参数；不同 provider 支持的 settings 不同（provider 专属子类），不保证所有开关通用；不支持的开关可能报错或被忽略 | 在途 run 保留其运行开始时解析出的模型/参数；新 run 用新值；子代理按下文 |
| ③ | 调度与预算 | 改一个登记的查看时间、静默窗口、并发/模型预算 | **框架无原生调度**（Core/Harness 均无）；登记／到期可由配套engine或成熟调度设施管理，必要检测接入与剩余业务策略另核。并发/预算＝项目资源策略＋框架 `usage_limits` 等 | 同 A2：Pi 亦**无原生调度**（factory 禁止起 timer，`session_start` 起的 timer 随进程死亡）；调度配套与检测接入按具体层次选择 | 改登记值通常只改数据；改并发/预算可能改策略代码或配置；**无框架级"改一处即全生效"** | 既有登记**候选**保留旧值（快照）或改后重读（重写）——两种都属候选，未定；已在外部调度排队/已触发的项不追溯 |
| ④ | 工具接入与权限 | 配置已有工具、撤销文件/网络操作资格 | 启用已有工具＝在 capability/toolset/工具集配置中增删（如 `FileSystem(tools=[...])` 等，**只限文件工具、非 OS 沙箱**）；新工具＝写代码注册函数工具；撤销＝Host 检查当前 capability | 启用已有工具＝`--tools/--no-tools/--extension...`、`defaultTools` 设置；新工具＝写 extension（`registerTool`）；撤销＝Pi 侧 extension `tool_call` 可 block，但 extensions **以完整系统权限运行、非沙箱** | 启用已有工具通常只配置；**实现新工具必须代码**；权限变更**不能只改提示词** | 权限撤销是**实时资格**，不因历史 receipt 恢复；配置回退**是否重新授权须单独核对**（见 §6 场景 2） |
| ⑤ | 认知参数与长期设定 | 检索/整理参数、投影版本或 Calibration | 检索/整理为**项目逻辑**（框架只有通用 `Memory`/`ConversationSearch`/`ProcessHistory` 等接入点）；投影＝**Versioned Base Projection ＋ 慢变 Subject Calibration**，属项目本体 | 同 A2：认知本体不在任一框架内；A1 不改变该判定 | 工程参数多为配置/数据；**Calibration 变更须长期证据＋主体显式认领＋Host 签发 receipt**，Base 变更属显式迁移、版本化 | **历史 Annotation 保留当时投影/校准版本**，不回写；新消费用新版本；Harness/框架不替主体认领 |
| ⑥ | 流程与结构 | 本人任务/子代理分工、任务执行逻辑、记忆对象/数据结构 | 子代理组成可由 `SubAgents` 配置；但任务生命周期、记忆对象类型、数据结构＝**代码**，结构变更常需**迁移** | A1 另需 Python↔Node 桥与两套会话/账本归口；**Pi 无原生子代理原语**，多进程编排＝代码 | 组合类可配置；新能力/结构改动**需代码/重启/迁移** | 在途任务与已启动子代理按下文；结构调整不能靠"配置"掩盖 |

## 3. 六类分项说明（影响面·校验·框架能力与增补）

每项回答：对已有 session、在途任务、已登记触发、子代理的影响；由谁校验并留版本/回退记录；框架已有能力与必须增加的适配。

### ① 内容与设定

- **内容存在哪里、谁读**：内容本身不是框架对象，是**项目数据**。A2 由编排侧在请求前把内容注入（PydanticAI 动态 instruction 函数 / `ProcessHistory` / `How` 上下文）；A1 还多一条 Pi 资源路径（`~/.pi/agent/` 与 `.pi/` 下的 `SYSTEM.md`/`APPEND_SYSTEM.md`/`AGENTS.md`/skills/prompts，由 `ResourceLoader` 提供，项目级于 project trust 通过后加载）。**同一个"表达偏好"在 A1 可能有两个读取点**，须指定哪个为准（无共享契约）。
- **旧历史与当前指令的区别**：standing system_prompt或普通消息可能保留旧文本，当前instructions另行求值，不能统一答“会”。PydanticAI 文档明确：`message_history` 非空时**不重新生成系统提示**；首个 `ModelRequest` 的系统提示是"standing"，后续请求里的是"mid-conversation instruction"，就地保留、不并入系统提示。因此**改内容不保证改变一个进行中会话早段已经携带的指令文本**，不能由此推导必须重建历史；ReinjectSystemPrompt用于缺失system prompt，不承诺替换已有旧prompt。Pi 侧 `session.systemPrompt` 可读当前有效系统提示（含尚未发出的改动），会话重建可能被 compaction 摘要。
- **影响**：已有 session——下一请求起读取新动态值，早段旧文本仍在历史；在途任务——其 run 的历史视为快照；已登记触发——无直接关系；子代理——独立 history，按创建时读取的内容版本运行。
- **校验/版本/回退**：内容版本由**项目侧**记录（框架不版本化 instruction 文本）；回退＝项目把内容指回旧版本；须标注"该会话/该 run 使用的 content 版本"。
- **框架已有/必须增加**：已有＝动态 instruction 求值、上下文注入、Pi `SYSTEM.md`/resources；必须增加＝项目内容仓的版本/引用、A1 两侧读取点的归口与一致性校验。

### ② 模型与工具参数

- **参数支持面**：文档给出的分层是「模型默认 → agent → capability → run」，run 级最高且**可为每请求求值的 callable**；`max_tokens`/`temperature`/`timeout` 等是通用结构，但**各 provider 有专属 settings 子类**（如 Google 专属），**不承诺所有开关对所有模型通用**，也不承诺不支持项一定报错而非被忽略。工具超时在 agent spec 里是 `tool_timeout`（默认工具超时）；重试有独立预算。
- **A1 的双出口问题**：A1 里编排 run 与被委派的 Pi run 是**两个模型/工具循环**，两侧各有模型出口与参数来源；"换模型"可能只落到一侧，模型调用是否翻倍须设计（framework-06 补充报告 §4）。
- **影响**：在途run使用快照还是动态重新求值是候选策略；callable可在下一普通请求读取新值，不能自动视为冻结；子代理按委派创建时的预算（PydanticAI `SubAgents` 有 per-delegate `max_calls`/`timeout_seconds`/`usage_limits`）运行；Pi 侧由进程启动参数/`models.json` 决定。
- **校验/版本/回退**：参数变更须记录"哪个 run 用了哪组设置"；PydanticAI `RunContext`/`AgentRun.metadata` 可携带运行期标记供观测（现行文档声称）。
- **框架已有/必须增加**：已有＝分层 settings、run 级覆盖、provider 专属设置、Pi `models.json`/CLI；必须增加＝A1 两侧参数的映射与优先级、声明式参数文件（A2 可用 Agent Specs 的 YAML/JSON）与校验。

### ③ 调度与预算

- **归属**：PydanticAI Core/Harness **无原生定时/调度**；Pi 亦**无**（factory 禁止起 timer/watcher，`session_start` 起的 timer/watcher 随进程死亡，不构成重启可补检的调度）。→ **改一个登记的查看时间**本质是**改项目侧登记数据**，由外部调度到点触发新 run；"到点≠数据变了"，外部变化检测仍需接入来源。
- **静默窗口/并发/预算**：静默窗口＝项目通知策略；并发/模型预算＝项目资源策略（VPS 容量报告把资源列为待核验条件，不做数字排名）＋框架的 `usage_limits` 等（每 run/每委派）。Pi 侧并发＝宿主起多个进程，属项目编排。
- **影响**：既有登记／正在等候的工作**不会因改一处全局配置自动重排**——须明确"旧登记保留旧值 vs 改后重读"的候选策略；已完成效果不逆转；排队／已触发项是否撤销、重排或重查未定。
- **校验/版本/回退**：登记项与预算需项目侧版本记录；回退＝恢复旧登记值/旧预算。
- **框架已有/必须增加**：核心未提供完整服务；已有配套／engine与成熟设施可覆盖部分登记/取消/去重/补检，仍须核对来源检测与剩余适配【高】）。

### ④ 工具接入与权限

- **启用已有工具 vs 实现新工具**：启用已有工具＝配置层增删（A2 如 `FileSystem(tools=[...])`、工具集/capability 组成；A1 如 Pi `defaultTools`、`--tools/--no-tools`）；实现新工具＝**写代码**（A2 注册函数工具；A1 写 extension `registerTool`）。两者成本不同，不能混为一谈。
- **权限变更不能只改提示词**：撤销文件/网络操作资格须落在**受控检查点**——A2 是 Host hook/审批闸门（`requires_approval`/deferred 等；`FileSystem.root_dir` 只限文件工具，**不是 OS 沙箱**，`Shell` 不受其约束）；A1 是 Pi extension `tool_call` 可 block，但 extensions **以完整系统权限运行、非沙箱**，不经该扩展工具路径的动作（派生 shell、其它扩展、MCP）不受其约束。真正隔离要靠 OS/容器（项目侧）。
- **影响**：已有 session 的**下一请求前**工具变更才会声明给模型（PydanticAI 内置规则；Pi `session` 亦然，工具变更在下一次请求前声明）；在途工具调用若已通过检查，撤销**时点**决定它是否继续；子代理不继承超出委派 scope 的权限（Full 档表述，属候选）。
- **校验/版本/回退**：权限是可撤销的**实时资格（capability）**，不与历史 receipt 混同（00c §9.1：receipt「不自带未来权限」）。**配置回退是否重新取得已撤销权限必须单独核对**——若权限被实现为"配置开关"，回退配置可能隐含恢复，须改由独立权限状态承载。
- **框架已有/必须增加**：已有＝hook/审批位点、工具集配置、extension block；必须增加＝域内 capability 校验与 receipt 签发（项目侧）、撤销传播、OS/容器隔离（均未验）。

### ⑤ 认知参数与长期设定

- **工程参数 vs 须主体认领**：检索/整理预算、候选数、freshness 阈值等属**工程参数**（可配置）；Self Model／Calibration需主体认领，多方Common Ground另需共同确认，域不能互换。PydanticAI 的 `Memory`（按 namespace）/`ConversationSearch`/`ProcessHistory` 只是通用接入点，**不是故渊的检索/整理本体**。
- **投影/Calibration 边界（不可越线）**：V/A Projection＝**Versioned Base Projection ＋ slow-changing Subject Calibration**；Base 属系统测量坐标系，配置固定、显式迁移、版本化，**普通模型输出不能改**；Calibration 有长期证据、provenance、**显式主体认领**，独立版本，**不能随单轮 Mood/Emotion 改变**。→ 界面能写值**不等于**可作任意单轮情绪滑块。
- **历史可比性怎样保持**：Aφect Annotation 保留发生/编码时的判读与当时所用 Base/Calibration/表达映射版本；当前 Mood/Calibration **不改写当时记录**，重评产生新版本（00c §4.2/§7.1）。
- **影响**：已有 session/在途任务按**消费契约**可知 computed-through/as-of/版本/freshness，过旧降级（current/aging/stale/expired）；版本不兼容与时间陈旧分别暴露。
- **校验/版本/回退**：域内 authority 校验（主体决定＋Host 签发 receipt）；Calibration 长期证据门槛与历史分类仍 **OPEN（Q-MA-05）**。
- **框架已有/必须增加**：已有＝注入/消费接入点；必须增加＝版本化投影/校准管线、消费契约、主体认领路径（全部项目侧）。

### ⑥ 流程与结构

- **可通过配置组合 vs 需代码/重启/迁移**：可配置＝子代理组成（`SubAgents([...])`）、工具集/capability 组合、Agent Specs（YAML/JSON 声明）；需代码＝任务生命周期、流程逻辑、新记忆对象类型；需迁移＝记忆对象/数据结构变更。A1 另需**Python↔Node 桥＋两套会话/账本归口**，且 Pi **无原生子代理原语**，多进程编排必写代码。
- **影响**：已有 session——流程代码变更可能需新进程；在途任务——正在执行的旧逻辑不自动替换；已登记触发——登记结构变更可能需迁移；子代理——按创建时逻辑运行。
- **校验/版本/回退**：结构迁移须留版本与回退记录，由工程侧校验（非主体认领）。
- **框架已有/必须增加**：已有＝组合式能力/子代理/声明式 spec；必须增加＝任务/子代理业务层、结构迁移机制（framework-06 已列为项目剩余工作）。

## 4. 保存值 ≠ 当前生效值：机制与"使用者怎样知道生效范围"

| 机制（官方依据） | 含义 | 使用者怎样知道生效范围 |
|---|---|---|
| PydanticAI：模型级/agent 级 settings 在**构造时**确定；run 级在**run 开始时**确定；动态 callable 在**每请求前**求值 | 改磁盘/界面值不会自动改变已构造的 Agent 或已开始的 run | 运行期可读 `RunContext.model_settings` 等；须显示"该 run 实际使用的设置层" |
| PydanticAI：`message_history` 非空时**不重新生成系统提示** | 改了内容，进行中会话早段仍带旧指令 | 须能读取"该会话历史里实际携带的指令文本/版本" |
| Pi：settings 分 user（`~/.pi/agent/settings.json`）与 project（`.pi/settings.json`），**project 覆盖 user、资源列表合并**；项目配置于 **project trust 后**加载 | "哪个文件的值最终生效"取决于加载顺序与 trust | Pi 暴露当前有效系统提示 `session.systemPrompt`（只读）、`session.model`、`getActiveToolNames()`、`/session` |
| Pi：手动改 settings/keybindings/instructions/resources 后**须 `/reload`**；`/reload` **只启用新加的 `defaultTools`，不移除被删的、也不重新启用你手动关掉的工具** | **强证据：文件里删掉一个工具，重载后并不会让它失效** | 须读 `getActiveToolNames()` 而非设置文件；须明确"删除需要重启或显式操作" |
| A1：两侧各有一套配置（Python 编排側＋Pi 側），**无共享契约** | 同一改动可能只落到一侧，或两侧取值不一致 | 需要项目侧提供统一"有效配置"视图，否则使用者无法从单一界面判断 |

**小结**：框架都提供**接入点**与部分**运行期可读状态**，但**没有任何一个框架保证"改磁盘或界面值后，所有活跃 session、子进程、扩展自动同步"**。因此"使用者怎样知道生效范围"的候选答案是：**由项目侧维护并显示一份"当前有效配置/版本"视图（含每会话/每 run 的生效点与所用版本）**，而不是靠"保存成功"的提示。此视图的具体形态仍 OPEN，本报告不给出字段/接口。

## 6. 两个变更纸面场景

### 场景 1 · 长任务中改设定和模型

设定：一个虚构研究任务正在跑，同时有一个**只读子代理**在运行；用户此时（a）修改表达偏好、（b）切换模型。

| 观察点 | A2（PydanticAI Core＋按需 Harness） | A1（PydanticAI＋Pi 执行器） |
|---|---|---|
| 主对话**下一次请求** | 动态instructions可重新求值，采用新偏好取决于读活数据还是固定版本；standing system_prompt与普通历史旧文本分别处理，不能混用不新建prompt规则 | 同A2；只对Pi实际消费项投送新视图，不必用户两边手改 |
| 只读子代理**当前工作** | 子代理是**独立 run、独立 history**，其内容/模型在**创建时**确定→**继续按旧设定/旧模型跑完**；只有新建子代理才用新值 | 同 A2；若子代理是另起的 Pi 进程，其模型/资源由该进程启动参数决定→**进程内不随宿主改动** |
| 任务**重启后**读取什么 | 从序列化的 `message_history` ＋任务/作品记录恢复；若历史带旧指令，重启**可能重新采用旧文本**，除非显式重建注入并带 content 版本 | 两侧各自恢复：编排侧 `message_history`＋`StepPersistence`；Pi 侧 session entry tree（可能被 compaction 摘要）。**两套会话无共享契约** |
| 旧内容与新设定**怎样区别** | 靠**项目侧 content 版本/watermark**（"该会话/该 run 用哪个版本"），**不能靠比对提示词文本差异** | 同 A2，另需标记 Pi 侧资源版本；两侧版本须对齐 |
| 生效点小结 | 内容／参数可能下一普通请求动态求值，也可采用run版本快照；静态资源重载与provider悬停续接另验，策略未定 | 同上，增加实际消费项的映射与加载边界 |

> 此场景刻意不画"界面→配置→agent"直线：至少存在「历史是否重生系统提示」「子代理独立 history」「A1 两侧配置」三处分叉。

### 场景 2 · 撤销工具资格并调整定时查看

设定：任务在**等明天查看某个虚构论坛**；用户（a）**撤销写文件资格**、（b）**修改查看时间**。

| 环节 | A2 | A1 | 必须单独核对的点 |
|---|---|---|---|
| 既有**登记** | 登记是项目数据；改查看时间＝改登记值。候选策略：旧登记保留旧值（快照）或改后重读（重写），二者未定 | 同 A2（Pi 无原生调度，登记在项目/外部） | 已完成效果不逆转；排队／已触发项的撤销或重查仍待设计；去重/补检机制仍 OPEN（Q-MA-04） |
| **下一次受控工具调用** | Host 在调用前检查**当前 capability**：写文件资格已撤销→**拒绝**（不是靠改提示词）；A2 `FileSystem(root_dir=...)` 只限文件工具、非 OS 沙箱 | 同 A2；Pi 侧由 extension `tool_call` block，但 extensions 非沙箱，绕过该路径的动作不受约束 | 撤销发生的**时点**：若工具调用已通过检查，撤销是否中止在途调用属契约，未定 |
| **已完成效果** | 已写入的文件/外部效果**保留**，撤销不反向执行；历史 receipt **保留但不再授予权限** | 同 A2 | 不得"靠重放补编成功"，也不得指望撤销自动回滚（framework-06 已定） |
| **配置回退** | **单独核对**：若"写文件资格"被实现为一个配置开关，回退配置**可能隐含重新授权**→须把撤销实现为**独立权限状态**，回退内容配置不得连带回权限 | 同 A2（且两侧各有一套配置，回退更须指明退哪一侧） | 讨论记录 §4 已列："撤销权限不能因回退配置隐含重新授权" |

## 7. 边界纪律（不因"能写值"而越线）

- **设定编辑 ≠ 认领 Self Model ≠ 确立他人 Fact ≠ 多方 Common Ground**（00c §9）：普通正文"我认可了"没有权威；关于他人的内容最多成为"我的理解"；共同理解需参与方确认。
- **Calibration 是慢变、版本化、需主体认领的独立层**：有长期证据、provenance、独立版本；**不能随单轮 Mood/Emotion 改变**，不能回写 Base 或命名维度；界面能写值**不使其成为任意单轮情绪滑块**（ADR-001）。
- **原始经历／工具回执不随"改设定"静默重写**：Evidence 只增不改；历史 Annotation 保留当时判读与版本；重评产生新版本，不恢复旧数值冒充现在（00c §4.2/§7.1）。
- 机制细节仍 **OPEN**，本报告不替用户裁决，也不产生最终字段/配置键/表结构/API/完整状态机。

## 9. 一项影响选择的窄验证建议（CANDIDATE，未执行）

**问题**：六类改动里最影响"哪个更好改"判断的，是**"配置编辑是否/何时对运行中对象生效"**——尤其 Pi v1.0.4 文档声称"`/reload` 不移除被删工具"，以及 A1 两侧配置无共享契约。静态文档回答不了。

**做法（离线、脚本化模型桩、无网络、不接 Serein/产品库）**：
- (a) Pi：起一个长驻 `--mode rpc` 会话，`defaultTools` 含某工具；编辑设置**删除**该工具后发 `/reload`，读 `getActiveToolNames()`，观察该工具是否**仍存在**（验证"删除不生效"）；
- (b) 同会话内改一处 instructions/资源，观察**下一请求**是否采用新值、`session.systemPrompt` 是否变化；
- (c) PydanticAI：改变动态 instruction 的数据源，观察下一请求生效、而已有 `message_history` 是否**仍带旧文本**。

**通过条件**（全部满足）：能**区分**"保存值/文件值"与"当前有效值"，并给出两者的可读来源；能复现"删除工具在 reload 后不失效"或明确推翻。

**理由**：若 (a)/(c) 成立，则"保存成功≠生效"是**可被使用者观测**的事实，界面必须显示"当前有效配置/版本"；这直接影响用户原问的答复边界。**本轮不运行，仅给建议与通过条件。**
